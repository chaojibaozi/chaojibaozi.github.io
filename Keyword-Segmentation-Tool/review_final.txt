【C-NEW-1】detectIndustry() 在【每个关键词】上重建 35 条行业正则，性能灾难
------------------------------------------------------------------------------
  位置：index.html 第 860–863 行（函数 detectIndustry，定义于 819 行）
  问题代码：
    for (const [pattern, industry] of industryMap) {
      const re = new RegExp(pattern);          // ← 每条关键词都重建整个 industryMap
      if (re.test(text)) return industry;
    }
    // industryMap 含 35+ 个行业、每个模式含大量关键词，是【静态】数据

  现象（Node 基准，5000 次调用）：
    ORIGINAL detectIndustry ×5000 : 476 ms，期间构造 RegExp 180,000 次（≈36 次/调用）
    PATCHED  （正则预编译一次） ×5000 :  99 ms，期间构造 RegExp     36 次
    ⇒ 仅此一处即慢约 4.8 倍，且每次分类都重复编译约 N×35 条正则。

  影响：分类延迟主要来自此处与 discoverDomainVocab 的 n-gram 重算（见 C-NEW-2）。
        classify() 在每条关键词内都会调用 detectIndustry，因此代价被乘以关键词总数。

  修复建议（已验证有效）：
    将 industryMap 的正则预编译为模块级常量，仅编译一次：
      const _IND_RE = industryMap.map(([p,i])=>[new RegExp(p),i]);
      // 循环改为 for (const [re,industry] of _IND_RE) if(re.test(text)) return industry;
    预计该处性能提升 4~5 倍，且不影响分类结果。


【C-NEW-2】整批分类性能不达标，1 万词约需 60 秒以上（UI 冻结）
------------------------------------------------------------------------------
  位置：index.html 第 1315 行 runClassification()（及被它调用的
        discoverDomainVocab 第 1136 行、detectIndustry 第 819 行）
  实测（Node，真实代码路径）：
    1500 个关键词 runClassification ≈ 9307 ms（≈ 6.2 ms/词）
    推算：10,000 词 ≈ 60 秒+（主线程同步执行，页面卡死，无法操作）

  根因（两处，均应缓存）：
    a) detectIndustry 每词重建 35 条正则（见 C-NEW-1，已证明 4.8x 冗余）。
    b) discoverDomainVocab() 在【每次】runClassification 都重新生成所有 n-gram
       （对每条关键词做 2/3/4-gram 组合，复杂度约 O(N·L³)），即便词典与词包
       未变也照算。其结果 state.domain / state.domainFreq / state.learned
       完全可缓存，仅在“关键词列/词典/词包”变化时重算。

  影响：用户导入稍大的文件（数千行）即出现明显卡顿；超过约 1 万行基本不可用。
       这是“能用但难用”的核心瓶颈。

  修复建议：
    1) 按 C-NEW-1 预编译行业正则；
    2) 给 discoverDomainVocab 增加缓存键（如基于 keywordCol + 词包哈希 +
       词典哈希），未变化时直接复用 state.domain；
    3) 若仍需进一步优化，可对 runClassification 做分片 + requestIdleCallback /
       Web Worker，避免阻塞渲染。

【M-NEW-1】aiClassify() 仅改写 cat/source，派生列全部“过期”且自相矛盾
------------------------------------------------------------------------------
  位置：index.html 第 1371–1373 行（aiClassify 末尾对每条结果的处理）
  问题代码：
    state.results.forEach(r=>{
      const c=map[r.kw];
      if(c&&nameToId[c]){ r.cat=nameToId[c]; r.source='AI'; hit++; }  // ← 只改这两项
    });
    // 未重算：dimLabel / intent / stage / quality / accountSuggestion /
    //          industry / conf / rule

  现象（Node 复现，把“苹果手机”在离线分类后人工改 cat 为 competitor 模拟 AI）：
    改前: {"cat":"brand",  "intent":"informational","stage":"awareness",
           "dim":"品牌+产品","conf":60,"quality":7,"acct":"计划:通用-品牌词|单元:引流词|..."}
    改后: {"cat":"competitor","intent":"informational","stage":"awareness",
           "dim":"品牌+产品","conf":60,"quality":7,"acct":"计划:通用-品牌词|单元:引流词|..."}
    ⇒ 一级分类已变“竞品词”，但 搜索意图/购买阶段/信号维度/置信度/质量/账户结构
       仍显示旧“品牌词”的派生值，表格多列彼此矛盾。

  影响：AI 分类的“卖点”是更准的一级分类，但配套分析（意图/阶段/维度/账户结构/
       行业/置信度）不跟随更新，用户看到的是自相矛盾的 SEM 结论，降低对 AI 功能的信任。

  修复建议：AI 改写 r.cat 后，对该结果调用与离线一致的派生计算，例如：
    r.dimLabel = ...; r.intent = detectIntent(r); r.stage = detectBuyingStage(r);
    r.quality = computeQualityScore(r); r.accountSuggestion = suggestAccountStructure(r.kw,r);
    r.industry = detectIndustry(prodTerm,r.kw); r.industryTags = detectIndustryTags(...);
    r.conf = ...（按 best/second 重新计算）;  r.rule = ...;
  或更直接：AI 改 cat 后，对受影响结果重新跑一遍 postProcessResults 的派生步骤。


【M-NEW-2】readDictFromUI() 不校验置信度阈值，清空输入框会得到 NaN
------------------------------------------------------------------------------
  位置：index.html 第 1605 行（readDictFromUI 内）
  问题代码：
    state.confTh = parseInt($('confTh').value, 10);   // ← 无 clamp / 无 NaN 兜底
  对比：滑块的 oninput（第 1420 行附近）已做 Math.max(0,Math.min(100,...))，
        但“重新分类 / 关闭设置抽屉应用”走 readDictFromUI 时并未做同样保护。

  现象（Node 复现）：把 confTh 输入框清空后调用 readDictFromUI()，
        state.confTh = NaN（isNaN = true）。
  连锁影响：
    - renderStats 中 review 计数 = r.conf < NaN 恒为 false ⇒ “需复核”永远为 0；
    - 表格复核标记逻辑 r.conf < state.confTh 同样失效；
    - 统计面板“需复核”数字失真。

  修复建议：与 oninput 保持一致：
    const v = parseInt($('confTh').value, 10);
    state.confTh = isNaN(v) ? 60 : Math.max(0, Math.min(100, v));


【M-NEW-3】parseCSV() 丢弃孤立的 \r，导致相邻字段被错误合并
------------------------------------------------------------------------------
  位置：index.html 第 1053 行（parseCSV 非引号分支）
  问题代码：
    else if(c==='\r'){ /* skip */ }   // ← 单独的 \r 被直接丢弃
  现象（Node 复现）：
    输入 'a,b\rc,d'（经典 Mac 行尾，仅 \r）
    实际： [['a','bc','d']]   ← 'b' 与 'c' 被合并为 'bc'
    期望： [['a','b','c','d']] 或按 \r 分行
  影响：导入“经典 Mac 换行（\r 无 \n）”的 CSV 时，整行字段会被拼接，
       造成数据错乱（Windows CRLF / Unix LF 不受影响，仅 \r-only 受影响）。

  修复建议：把孤立 \r 当作行分隔符（与 \n 同处理）：
    else if(c==='\r'){ row.push(cur); rows.push(row); row=[]; cur=''; }
  （注：CRLF 场景先遇到 \r 已 push 空行？需确认：当前顺序 \r 先被本分支处理会
    在 CRLF 下多产生一个空行。正确写法应优先判断 \r\n：
      else if(c==='\r'){ /* 暂存，等下一个字符判断 */ }
      else if(c==='\n'){ row.push(cur); rows.push(row); row=[]; cur=''; }
    或统一先 replace(/\r\n?/g,'\n') 再按 \n 解析。）


【M-NEW-4】品牌+产品类关键词的“搜索意图”被误判为信息型（导航型丢失）
------------------------------------------------------------------------------
  位置：index.html 第 881–912 行 detectIntent()
  问题：detectIntent 的导航型分支要求 !dims.includes('产品')：
    if (dims.includes('品牌') && !dims.includes('产品') && !dims.includes('型号') && !dims.includes('属性'))
      return 'navigational';
    但“苹果手机”“华为笔记本”“小米电视”这类高频词，因“手机/笔记本/电视”命中
    产品词根（extraLen<=2 时记 core 维度=“产品”），dimLabel 含“产品”，
    导致导航型分支被跳过，最终落入默认 'informational'。

  现象（Node 复现）：
    "苹果手机"  => cat=brand, intent=informational, stage=awareness, dim="品牌+产品"
    （合理预期应为 intent=navigational / stage=decision 一类的“找品牌官网”意图）

  影响：品牌词是 SEM 最核心的导航/品牌词，意图与购买阶段被系统性低估，
       直接影响“搜索意图”“购买阶段”“账户结构建议”三列的正确性。

  修复建议：当 cat==='brand'（或命中品牌词典）时，应优先判定为导航型，
       不被“产品”维度压制，例如把导航型分支提前并在 dims 含品牌时直接返回
       navigational（除非同时含价格/促销等更强交易信号）。


【M-NEW-5】结果表格未渲染“置信度 / 需复核”标记（已计算却不显示）
------------------------------------------------------------------------------
  位置：index.html 第 1516 行（renderTable 内 const conf=... 已计算）
        与第 1522 行（行模板 tr.innerHTML 未包含 ${conf}）
        表头（第 230 行）亦无“置信度”列
  现象：renderTable 行模板仅有 9 个单元格（复选框/关键词/一级分类/质量/
        搜索意图/购买阶段/信号维度/命中规则/来源），置信度（conf）与“复核”徽标
        虽已计算却未插入任何单元格；表头也没有对应列。
  影响：用户只能在统计面板看到“需复核”的总数，无法在表格中逐行识别
       哪些词需要人工复核，复核工作流形同虚设。

  修复建议：在表头增加“置信度”列（如插入到“质量”之后），并在该列渲染
        `${conf}%` 与“复核”徽标（已有 conf/review 变量，直接拼入即可）。


【M-NEW-6】关键词列 / 信号维度列缺少溢出约束（长内容撑破布局）
------------------------------------------------------------------------------
  位置：index.html 第 230 行表头“关键词”列（width:15%，无 max-width/ellipsis）
        与第 100 行 CSS .dims{ white-space:nowrap; … }（无 max-width/overflow/ellipsis）
  现象：
    - 关键词单元格 <td style="font-size:12px;">…</td> 无宽度/省略号限制，
      超长关键词（如粘贴的长句）会把“关键词”列撑得很宽，#tableWrap 出现横向滚动，
      其余列被挤压、可读性下降。
    - 信号维度 <span class="dims">品牌+产品+价格+促销+长尾+地域</span>
      为 nowrap 且无省略号，超长标签同样溢出“信号维度”列。
  影响：导入含长文本/多维度命中词时，表格横向溢出、版式被破坏。

  修复建议：
    1) 关键词单元格加类并约束：
       .kw-cell{ max-width:240px; overflow:hidden; text-overflow:ellipsis; white-space:nowrap; }
       （hover 时可展开，参考 .rule-cell 的做法）
    2) .dims 增加 max-width 与省略号，或允许换行：
       .dims{ max-width:140px; overflow:hidden; text-overflow:ellipsis; }


【M-NEW-7】“取消全选”后导出为空，且筛选态与导出范围不一致（体验）
------------------------------------------------------------------------------
  位置：index.html 第 1534 行 toggleAllChecked() 与第 1186 行附近 exportXLSX()
  现象（Node 复现）：
    - 分类后 checkedUnchecked=null（=全选），导出 = 全部 N 条 ✅
    - 取消勾选 1 行 → 导出 = N-1 条 ✅
    - 点击“全选”复选框取消全选（toggleAllChecked(false)）→ checkedUnchecked=全部索引
      → 导出触发“请先勾选要导出的关键词”，导出 0 条
    - 即“取消全选”后再点导出得到空文件，容易让用户误以为功能坏掉。
  附加观察：导出范围取决于 checkedUnchecked（全选=全部结果 / 否则=未取消集合），
        与当前“分类筛选/图例筛选”只影响表格显示、不影响导出范围并存，
        用户筛选后点“全选+导出”会导出全部而非当前筛选视图（导出提示已说明“包含全部结果”）。

  影响：导出交互反直觉，存在“导出为空”的困惑场景。
  修复建议（可选）：
    - 默认“全选”状态下导出应提示“将导出全部 N 条 / 仅导出当前筛选 M 条”；
    - “取消全选”后可改为“导出当前已勾选（0 条）并提示”，或直接禁用导出按钮
      直到有勾选；或提供“导出当前筛选视图”开关。
