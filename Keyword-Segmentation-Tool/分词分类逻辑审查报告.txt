审查对象 : D:\BianCheng\Keyword-Segmentation-Tool\index.html（主程序，约 1.3 MB / 1891 行）
审查范围 : 双向最大匹配分词函数 segmentFMM/segmentBMM/segment、
           核心分类函数 classify()、BASE 词典体系与评分竞争机制
审查方式 : 从 index.html 抽取含 function classify 的 <script> 块，
           在 Node 中以 DOM 桩（自引用 Proxy）离线执行原程序逻辑，
           批量跑 2116 条覆盖 40+ 行业的关键词，量化误判。
审查日期 : 2026-07-24
结论摘要 : 用户反馈的“网络词被分到公司词”问题属实，根因是
           (1) BASE.company 词典被大量“平台/网站/论坛/社区/媒体/电商”
               等网络词污染；(2) 分类采用“整词正则+最高分取胜”，
               company=102 的分值高于产品精确匹配 core=94，
               即使关键词本身就是产品词也会被判为公司词。
           此外分词函数 segment() 与 classify() 完全脱节（分类未调用分词），
           且存在 geo 子串过匹配、属性词压过产品词两处次级缺陷。

二、分词逻辑审查（segmentFMM / segmentBMM / segment）
------------------------------------------------------------------
源码位置：index.html 第 782–816 行。

【S1｜关键｜分词与分类完全脱节】
  segment() 的返回值在 classify() 中**没有任何调用**。classify() 全程
  基于整词正则 / 子串匹配（reCompany.test(k)、k.includes(p) 等）决定类别，
  双向最大匹配分词对最终分类结果零贡献。
  → 这意味着：即便把 segment() 改得再完美，分类结果也不会改变；
    用户感知到的“分词错误”，实质是“分类字典/评分”问题，而非分词算法本身。
  → segment() 在当前主流程里属于**死代码**，应明确文档化其用途，或接入分类。

【S2｜算法｜BMM/FMM 平局无次级判据】
  segment(text,dictSet) 以 `fmm.length<=bmm.length? fmm : bmm` 取“词数少者”。
  当两者词数相等时恒取 FMM，仅以词数为唯一判据，缺少第二标准
  （如单字 token 数最少、或词典语义权重）。对“研究生/生活”类歧义串可能取错。
  影响：低（因未接入分类），但若后续用于分类须补充判据。

【S3｜设计｜单词典匹配丢失多信号】
  segmentFMM/BMM 仅接受单个 dictSet，未Union(品牌+产品+地域+属性+公司)。
  例“北京空调厂家”若只喂 product 词典，会拆成[北京,空调,厂家]（北京→单字碎片），
  在分词阶段即丢失 geo/company 信号。应为多词典联合或逐词典分词。

【S4｜鲁棒性｜无重叠/前缀处理】
  FMM/BMM 贪心取最长匹配，对词典中存在包含关系的前缀（如“智能手机”/“手机”）
  能取最长，但对词典未收录的新词直接回退到单字（见 S5），无未登录词兜底。

【S5｜鲁棒性｜单字回退产生无意义碎片】
  无词典命中时 `longest=text[i]` 输出单字，既无语义也无法用于分类，
  还会抬高 token 数，间接让 segment() 偏向另一方向。建议对未登录词做
  Bigram 或整段回退，而非逐字碎裂。

【S6｜一致性｜注释与实际行为不符】
  第 814 行注释称“BMM handles suffix prefixes better”，但代码
  `fmm.length<=bmm.length?fmm:bmm` 仅在 BMM 严格词数更少时才选 BMM，
  无语言学依据，也与注释暗示的“后缀优先”不符。属可维护性缺陷。

三、分类根因分析（classify / 词典 / 评分竞争）—— 用户问题主因
------------------------------------------------------------------
源码位置：classify() 第 1185–1313 行；BASE 词典第 663–735 行；
          评分竞争第 1287–1288 行（取最高分胜出）。

3.1 评分竞争机制（取最高分即胜）
  各信号分值（节选）：
    价格(强)122 > 疑问120 > 口碑116 > 活动114 > 地域108 > 人群104
    > 公司102 > 电话100 > 厂家98 > 价格(弱)96 > 属性92 > 品牌90
    > 核心(精确)94　核心(短修饰)60　长尾58　型号110/100　通用12
  ⚠ 致命点：company=102  >  core(精确)=94  >  core(短)=60  >  longtail=58。
  即：只要关键词含一个“公司词典”子串，哪怕它本身就是产品词，
      公司词也必然胜出——因为 102 高于产品所有档位。

3.2 BASE.company 词典被网络词污染（定义始于第 718 行，约 5180 条）
  公司词典里混入了大量“互联网/社交/内容/电商”通用词，且其中多数
  同时存在于 BASE.product（第 663–710 行），造成同词双归属：
    · 游戏平台 / 游戏论坛 / 游戏社区 / 游戏媒体 / 游戏资讯网站
    · 直播平台 / 社交平台 / 社交软件 / 资讯平台 / 资讯网站
    · 自媒体 / 新媒体 / 公众号 / 社群 / 社区 / 论坛 / 短视频
    · 网店 / 淘宝店 / 天猫店 / 跨境电商 / 社区电商
    · 驾校 / 全屋定制 / 度假村 / 猎头 / 劳务派遣 等服务业词
  这些词本应是产品词/核心词/长尾词，却因被写进 company 词典，
  在 classify() 中以 102 分碾压产品词（94/60/58）胜出。

  典型证据：
    “直播平台” —— 同时命中 company(102) 与 product 精确匹配 core(94)
                  → 取最高分，判【公司词】。（产品精确匹配反而输给公司）
    “自媒体”   —— 同时命中 company(102) 与 product core(94)
                  → 判【公司词】。
    “游戏论坛” —— company 含“游戏论坛”(102)，product 仅含“论坛”(58)
                  → 判【公司词】。

3.3 次级缺陷 A：地域词子串过匹配（geo）
  geo 匹配用 `k.includes(g)`（第 1203 行），无边界检查。
  短行政区名（朝阳/河东/南开/花都）会嵌入普通词误命中：
    “朝阳产业”→地域(含“朝阳”)   “河东狮吼”→地域(含“河东”)
    “南开大学”→地域(含“南开”)   “花都汽车城”→地域(含“花都”)
  属字典+匹配方式缺陷，与分词无关。

3.4 次级缺陷 B：属性词压过“修饰+产品”（attribute）
  当“属性修饰+产品词根”组合时，attribute=92 高于 core(短修饰)=60：
    “变频空调” → 含“变频”(属性92) + “空调”(core=60) → 判【属性词】
    “防水涂料” → 含“防水”(属性92) + “涂料”(core=60) → 判【属性词】
    “实木家具” → 含“实木”(属性92) + “家具”(core=60) → 判【属性词】
  注：纯“变频器”因整词命中产品(精确94>属性92)判核心正确，
      说明第 1263–1266 行的“精确匹配压属性”规则只对“整词=产品”有效，
      对“修饰+产品”组合失效。

六、修复建议（按优先级）
------------------------------------------------------------------
【P0】净化 BASE.company 词典
  · 将“平台/网站/论坛/社区/媒体/自媒体/公众号/社群/短视频/网店/电商/
    直播/游戏内容”等网络词从 company 移出，归还 product/longtail，
    或新增独立“渠道/平台”类，避免与产品词双归属。
  · 同步清理“驾校/全屋定制/度假村/猎头/劳务派遣”等服务业词。
  · 建议用脚本对 BASE.company ∩ BASE.product 做交集扫描，自动化清理。

【P0】修正评分竞争，使产品精确匹配不被公司词压制
  · 方案A（推荐）：引入“产品词根命中优先”——当关键词命中 product 词根
    且未命中明显的法人实体后缀（如“有限公司/医院/厂/诊所”）时，
    company 不应胜出；或令 core(精确) 分值 > company（如 94→110）。
  · 方案B：company 匹配增加边界/后缀约束（仅当含“公司/有限公司/厂/
    医院/诊所/工作室”等法人后缀才判公司），杜绝“游戏论坛”式裸词命中。

【P1】修复属性词压产品词
  · 当“属性修饰+产品词根”同时存在时，core 应高于 attribute：
    将 core(短修饰) 由 60 提升至 ≥ attribute(92)，或新增规则
    “若已命中产品词根，attribute 不单独胜出”。

【P1】修复 geo 子串过匹配
  · geo 匹配加边界（正则词边界/白名单），或建立“短地名”子表
    仅在确为地名语境时命中，避免“朝阳产业”“南开大学”误判。

【P2】厘清分词与分类的关系
  · 若计划让 segment() 驱动分类：将分词结果接入 classify()，并改为
    多词典联合分词（S3）、补充平局次级判据（S2）、未登录词兜底（S5）。
  · 若维持当前整词正则方案：将 segment() 移出主流程或明确标注为
    未使用，避免后续维护者误以为分类依赖分词。

------------------------------------------------------------------
七、结论
------------------------------------------------------------------
1. 用户反馈属实：网络词被分入公司词是真实且系统性的缺陷，专项误判率 12.3%。
2. 主因并非分词算法，而是 (a) company 词典被网络词污染 + (b) 评分竞争中
   company=102 高于产品所有档位，导致“含公司词典子串即判公司”。
3. 分词函数 segment() 与分类逻辑脱节，当前不参与分类，属死代码；
   其自身也存在单词典、无次级判据、单字回退等算法瑕疵，需择机治理。
4. 次级缺陷：geo 子串无边界过匹配、属性词压过“修饰+产品”组合。
5. 修复重点应落在词典净化（P0）与评分/匹配约束（P0/P1），
   可在不改分词架构的前提下，先消除绝大多数误判。
