【C-NEW-1】detectIndustry() 在每个关键词上重建 37 条行业正则（性能灾难）
--------------------------------------------------------------------------------
  位置：index.html 第 817 行（函数 detectIndustry，行业正则循环在第 858–861 行）
  问题代码：
    for (const [pattern, industry] of industryMap) {        // industryMap 含 37 个行业
      const re = new RegExp(pattern);                       // ← 每条关键词都重建全部 37 条
      if (re.test(text)) return industry;
    }
    // industryMap 是【静态】数据（37 条超长正则），却未预编译
  实测（Node 桩，5000 次调用）：338 ms，期间构造 RegExp 约 185,000 次。
  影响：classify() 在每条关键词内都会调用 detectIndustry（第 1304 行），
       正则编译代价被乘以关键词总数。
  修复建议（已验证可行）：将 industryMap 预编译为模块级常量，仅编译一次：
    const _IND_RE = industryMap.map(([p,i])=>[new RegExp(p,'i'),i]);
    // 循环改为 for (const [re,industry] of _IND_RE) if(re.test(text)) return industry;
  预期收益：该处性能提升约 4~5 倍（历史基准 476ms→99ms）。


【C-NEW-2】整批分类性能不达标，万词约 44 秒（主线程同步 → UI 冻结）
--------------------------------------------------------------------------------
  位置：index.html 第 1317 行 runClassification()
        （调用 discoverDomainVocab 第 1135 行、detectIndustry 第 817 行）
  实测（Node 桩，真实代码路径）：
    1800 个关键词 runClassification ≈ 7996 ms（≈ 4.4 ms/词）
    ⇒ 推算 10,000 词 ≈ 44 秒+（主线程同步执行，页面卡死无法操作）
    discoverDomainVocab 单次（1800 词）≈ 585 ms，且【每次 runClassification
    都重算全部 n-gram（O(N·L³)）】，即便词典与词包未变也照算（无缓存键）。
  根因（两处，均应缓存）：
    a) detectIndustry 每词重建 37 条正则（见 C-NEW-1）；
    b) discoverDomainVocab 在【每次】分类都重新生成 n-gram / 词频 / 词根
       （第 1135–1170 行），结果 state.domain / state.domainFreq / state.learned
       完全可缓存，仅在“关键词列 / 词典 / 词包”变化时重算。
  影响：用户导入数千行文件即明显卡顿；超过约 1 万行基本不可用。
  修复建议：
    1) 按 C-NEW-1 预编译行业正则；
    2) 给 discoverDomainVocab 增加缓存键（keywordCol + 词包哈希 + 词典哈希），
       未变化时直接复用 state.domain；
    3) 若需进一步优化，可对 runClassification 做分片 + requestIdleCallback /
       Web Worker，避免阻塞渲染。

【M-NEW-1】aiClassify() 仅改写 cat/source，派生列全部“过期”且自相矛盾
--------------------------------------------------------------------------------
  位置：index.html 第 1370 行（aiClassify 末尾对每条结果的处理）
  问题代码：
    state.results.forEach(r=>{
      const c=map[r.kw];
      if(c&&nameToId[c]){ r.cat=nameToId[c]; r.source='AI'; hit++; }  // ← 只改这两项
    });
    // 未重算：dimLabel / intent / stage / quality / accountSuggestion /
    //         industry / industryTags / conf / rule
  实测（Node 桩，把“苹果手机”用 AI 改为竞品词后）：
    改前: {cat:brand,  intent:informational, stage:awareness, dimLabel:品牌+产品,
           conf:60, quality:7, acct:计划:通用-品牌词|单元:引流词|...}
    改后: {cat:competitor, intent:informational, stage:awareness, dimLabel:品牌+产品,
           conf:60, quality:7, acct:计划:通用-品牌词|单元:引流词|...}
    ⇒ 一级分类已变“竞品词”，但搜索意图/购买阶段/信号维度/置信度/质量/账户结构
       仍显示旧“品牌词”的派生值，表格多列彼此矛盾。
  影响：AI 分类把“更准的一级分类”作为卖点，但配套 SEM 分析不跟随更新，用户看到
       自相矛盾的结论，降低对 AI 功能的信任。
  修复建议：AI 改写 r.cat 后，对该结果调用与离线一致的派生计算：
    r.dimLabel=...; r.intent=detectIntent(r); r.stage=detectBuyingStage(r);
    r.quality=computeQualityScore(r); r.accountSuggestion=suggestAccountStructure(r.kw,r);
    r.industry=detectIndustry(prodTerm,r.kw); r.industryTags=detectIndustryTags(...);
    r.conf=...（按 best/second 重算）; r.rule=...;
    或更直接：AI 改 cat 后，对受影响结果重新跑一遍 postProcessResults 的派生步骤。


【M-NEW-4】品牌+产品类关键词的“搜索意图”被误判为信息型（导航型丢失）
--------------------------------------------------------------------------------

  问题代码：
    if (dims.includes('品牌') && !dims.includes('产品') && !dims.includes('型号') && !dims.includes('属性'))
      return 'navigational';

【M-NEW-2】readDictFromUI() 不校验置信度阈值，清空输入框会得到 NaN
--------------------------------------------------------------------------------
  位置：index.html 第 1652 行（readDictFromUI 内）
  问题代码：state.confTh = parseInt($('confTh').value, 10);  // ← 无 clamp / 无 NaN 兜底
  实测（Node 桩）：把 confTh 输入框设为 '' 后调用 readDictFromUI() → state.confTh=NaN；
        设为 '150' 后 → state.confTh=150（未 clamp）。
  连锁影响：renderStats 中“需复核”计数 = r.conf < NaN 恒为 false ⇒ 永远为 0；
        表格复核标记逻辑同样失效；统计面板“需复核”数字失真。
  风险评级：低（confTh 为 range 输入，用户无法在 UI 清空；仅当代码将 value 置空时触发）。
  修复建议（防御性，与滑块 oninput 保持一致）：
    const v = parseInt($('confTh').value, 10);
    state.confTh = isNaN(v) ? 60 : Math.max(0, Math.min(100, v));


【M-NEW-3】parseCSV() 丢弃孤立的 \r，导致相邻字段被错误合并
--------------------------------------------------------------------------------
  位置：index.html 第 1051 行（parseCSV 非引号分支）
  问题代码：else if(c==='\r'){ /* skip */ }   // ← 单独的 \r 被直接丢弃
  实测（Node 桩）：
    输入 'a,b\rc,d'（经典 Mac 行尾，仅 \r）
    实际： [['a','bc','d']]   ← 'b' 与 'c' 被合并为 'bc'
    期望： [['a','b'],['c','d']] 或按 \r 分行
  影响：导入“经典 Mac 换行（\r 无 \n）”的 CSV 时，整行字段被拼接，数据错乱
        （Windows CRLF / Unix LF 不受影响，仅 \r-only 受影响）。
  修复建议：把孤立 \r 当作行分隔符（与 \n 同处理），或先
        text.replace(/\r\n?/g,'\n') 再按 \n 解析。


【M-NEW-6】关键词列 / 信号维度列缺少溢出约束（长内容撑破布局）
--------------------------------------------------------------------------------
  位置：index.html 第 1531 行（renderTable 内 const colMaxWidths=[36,0,0,...]，
        关键词列 index=1 上限为 0）
        与 CSS 第 100 行（.dims{ white-space:nowrap; … } 无 max-width/overflow/ellipsis）
        关键词单元格（第 1567 行）<td style="font-size:12px;">…</td> 无 class/宽度/省略号
  实测（Node 桩）：超长关键词（300 字）measureTextWidth = 2100px；
        因 table 为默认 auto 布局且无 max-width，关键词列被撑宽，
        #tableWrap（overflow:auto）出现横向滚动，其余列被挤压。
  影响：导入含长文本/多维度命中词时，表格横向溢出、版式被破坏。
  修复建议：
    1) 关键词单元格加类并约束：
       .kw-cell{ max-width:240px; overflow:hidden; text-overflow:ellipsis; white-space:nowrap; }
       （hover 时可展开，参考已修复的 .rule-cell 做法）
    2) .dims 增加 max-width 与省略号，或允许换行：
       .dims{ max-width:140px; overflow:hidden; text-overflow:ellipsis; }


【M-NEW-7】“取消全选”后导出为空，且筛选态与导出范围并存（体验歧义）
--------------------------------------------------------------------------------
  位置：index.html 第 1585 行 toggleAllChecked() 与第 1602 行附近 exportXLSX()
  实测（Node 桩）：
    - 分类后 checkedUnchecked=null（=全选），导出 = 全部 N 条 ✅
    - 取消勾选 1 行 → 导出 = N-1 条 ✅
    - 点击“全选”复选框取消全选（toggleAllChecked(false)）→ checkedUnchecked=全部索引
      → 导出触发“请先勾选要导出的关键词”，导出 0 条（实测 toast=请先勾选要导出的关键词）
    - 即“取消全选”后再点导出得到空文件，容易让用户误以为功能坏掉。
  附加观察：exportXLSX 的 exportRows 直接取 visibleResults()（受搜索/类目筛选影响），
        但 renderTable 第 1570 行的提示文案写“导出 Excel 包含全部结果”，
        实际只导出【当前筛选视图】，提示与行为不一致（见下方“新增-1”）。
  影响：导出交互反直觉，存在“导出为空”的困惑场景。
  修复建议：默认“全选”状态下导出应明确提示“将导出全部 N 条 / 仅导出当前筛选 M 条”；
        或“取消全选”后禁用导出按钮直到有勾选；或提供“导出当前筛选视图”开关。


【新增-1】导出范围与界面提示文案不一致（导出仅当前筛选视图，却提示“包含全部结果”）
--------------------------------------------------------------------------------
  位置：index.html 第 1602 行 exportXLSX()（exportRows = visibleResults()）
        与第 1570 行提示文案“…导出 Excel 包含全部结果。”
  现象：当搜索框或分类筛选处于激活状态时，点击“导出 Excel”只会导出当前可见的
        筛选子集，而非“全部结果”。实测：在 search='小米' + 类目=品牌 的筛选态下
        导出仅得 2 行（全部 28 行中的子集），与“包含全部结果”文案矛盾。
  影响：用户可能误以为已导出全量数据，导致漏导。
  修复建议：要么导出时忽略筛选、真正导出全部；要么将提示文案改为
        “导出当前筛选/勾选的 N 条”，并保持与筛选状态一致。


【新增-2】列选择取消确认后，下拉框显示值与 state 不一致
--------------------------------------------------------------------------------
  位置：index.html 第 1726 行（$('colSelect').onchange）
  现象：onchange 内先判断 `if(state.results.length && !confirm(...)) return;`
        若用户取消确认，函数直接 return，但原生 <select> 的显示值已变为新选项，
        而 state.keywordCol 未变 → 下拉框显示“新列”但实际仍用“旧列”分类，
        状态与 UI 不一致，直至下次改变。
  影响：轻度困惑（数据列与显示不符）。
  修复建议：取消确认时将 sel.value 还原为 String(state.keywordCol)。
